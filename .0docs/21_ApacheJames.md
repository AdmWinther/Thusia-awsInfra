# Apache James Mail Server

## Overview

Apache James is an open-source mail server used in this project to handle email sending and receiving. It is configured to run in a Docker container and is managed by Docker Compose.

## Configuration

The configuration for Apache James is generated by Terraform and provisioned to the EC2 instance. The key configuration files are:

### `james-database.properties`

This file configures the connection to the MariaDB database. It specifies the JDBC driver, database URL, username, and password.

```properties
database.driverClassName=org.mariadb.jdbc.Driver
database.url=jdbc:mariadb://db-container/james_db
database.username=james_user
database.password=james_password
```

### `mailetcontainer.xml`

This file defines the mail processing logic. It is configured to:
-   Relay all outgoing mail through AWS Simple Email Service (SES).
-   Store a copy of sent emails in the user's "Sent" folder.
-   Handle local delivery for recipients within the same domain.
-   Manage error handling and bouncing of emails.

### `smtpserver.xml`

This file configures the SMTP listeners. The server listens on three ports:
-   **Port 25**: Standard SMTP, with STARTTLS enabled.
-   **Port 465**: SMTPS (SMTP over SSL).
-   **Port 587**: Submission port for email clients, with STARTTLS enabled.

All listeners are configured to use a PKCS12 keystore for TLS.

### `imapserver.xml`

This file configures the IMAP listeners. The server listens on two ports:
-   **Port 143**: Standard IMAP, with STARTTLS enabled.
-   **Port 993**: IMAPS (IMAP over SSL).

Both listeners use the same keystore as the SMTP servers.

## Initialization

The Apache James server is initialized using the `james_initialize.sh` script. This script is executed when the EC2 instance is first created. It performs the following actions:
1.  Adds the domain to the server, taken from the `domain_name` variable.
2.  Creates the service mailboxes — `admin`, `crm`, `joomla`, `api_joomla`, `fbl` and
    `dmarc-reports` — each with a password supplied from `terraform.tfvars`.

## File Generation Modules

The configuration files for Apache James are generated by Terraform modules located in the `___ShredModules___` directory. The naming convention for these modules is `file_gen_james_xxx`, where `xxx` corresponds to the name of the generated file.

The following files are generated by their respective modules:
-   `james-database.properties`
-   `imapserver.xml`
-   `james_initialize.sh`
-   `mailetcontainer.xml`
-   `smtpserver.xml`

Once these files are generated, the main Terraform configuration file (`main.tf`) provisions them to the AWS EC2 instance during the server setup process.

## Docker Integration

Apache James runs in a Docker container named `james`. The container is defined in the `docker-compose.yml` file and is part of the same Docker network as the other services. This allows it to communicate with the MariaDB database container.

## Keystore Management for TLS/SSL

James serves TLS on its SMTP and IMAP listeners from a **PKCS12 keystore**, mounted into
the container as `conf/keystore`. The keystore holds the same Let's Encrypt certificate and
private key that Nginx uses for HTTPS — there is no separate mail certificate.

### How the keystore is produced

`SSL_Agent.sh` (generated by `___ShredModules___/file_gen_SSL_Agent`) does the whole job on
the server, in one pass, right after certbot issues the certificate:

```bash
openssl pkcs12 -export \
  -in  /etc/letsencrypt/live/<domain>/fullchain.pem \
  -inkey /etc/letsencrypt/live/<domain>/privkey.pem \
  -name james -out <home>/keystore -passout pass:<james_keystore_password>
```

`openssl pkcs12 -export` writes a PKCS12 store directly, so no `keytool` step and no James
container are needed. PKCS12 is a portable standard (RFC 7292): a store written by OpenSSL
is read by the JVM without conversion.

`SSL_Fetch.sh` (from `file_gen_SSL_Fetch`) then copies the keystore and the four PEMs back
to `./SSL-certificates/` on your workstation over SCP, from where Terraform's file
provisioners deploy them on subsequent applies.

### The keystore password

The password lives in **one** place, the `james_keystore_password` variable in
`terraform.tfvars`. It is consumed by three generators, which is what keeps them in
agreement:

| Generator | Uses it for |
|---|---|
| `file_gen_SSL_Agent` | `-passout` when creating the keystore |
| `file_gen_james_smtpserver_xml` | the `<secret>` element on each SMTP listener |
| `file_gen_james_imapserver_xml` | the `<secret>` element on each IMAP listener |

Because all three read the same variable, they cannot drift. If the keystore is ever built
by hand with a different password, James fails to open it and TLS does not start.

> ⚠️ Do not use the password published in Apache James's own sample configuration. It is
> widely known and would let anyone who obtains the keystore file read the private key.

### Certificate coverage

The certificate must include the hostname mail clients connect to — the `mail.` subdomain,
which is also the MX target. The names in the certificate come from the
`certificate_subdomains` list in `terraform.tfvars`, so adding a name is a variable change.
Every name in that list must already resolve to the server: certbot validates each one over
HTTP-01, and a single unresolvable name fails the whole request.

Re-issuing the certificate with different names means rebuilding the keystore from the new
certificate — `SSL_Agent.sh` does this automatically, since it rebuilds on every run.

### Verifying a keystore

To confirm the store opens and holds a private key, using the same JDK James will use:

```bash
docker run --rm --entrypoint keytool \
  -v <path>/keystore:/tmp/keystore:ro \
  apache/james:jpa-3.8.2 \
  -list -keystore /tmp/keystore -storetype PKCS12 -storepass <james_keystore_password>
```

Expect a single `PrivateKeyEntry` under the alias `james`. With OpenSSL alone:

```bash
openssl pkcs12 -info -in keystore -passin pass:<james_keystore_password> -nokeys -noout
```

`Mac verify error: invalid password?` means the store was built with a different password
than the configuration expects.

### Rebuilding the keystore without the server

The keystore is derived entirely from `fullchain.pem` and `privkey.pem`, so it can be
rebuilt locally from the PEMs already in `SSL-certificates/` — no server and no certbot
run required. Use the same `openssl pkcs12 -export` command as above, then restrict it with
`chmod 600`: the file contains the private key.

### Historical note

Earlier revisions of this document described generating the keystore with
`keytool -genkey` inside a James container, then obtaining a certificate via a CSR
submitted to an external CA. That predates `SSL_Agent.sh`. `keytool -genkey` produces a
**self-signed** certificate, which mail clients reject as untrusted, and the CSR/CA round
trip is unnecessary now that certbot issues the certificate on the host. The procedure
above replaces it.
